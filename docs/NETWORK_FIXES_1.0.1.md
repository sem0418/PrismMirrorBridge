日期：2026-11-08。**真实 Windows + Prism 11.1.1 的 LegacyFTB 列表和 ATM10 8.5 完整导入：未实机验证。** 以下分别列出网络观测、程序改动与自动化验证，不把接口或单元测试当作桌面导入成功。

## LegacyFTB

### 证据与结论

用户报告的 IPv4 TLS 前重置、IPv6 超时，以及 Qt HTTP 状态 0，都没有取得 HTTP 响应，不能说明 XML 端点已变成 404 或已废弃。Prism 源码仍从 CreeperHost 的这两个地址取列表。

| 本次验证路径 | thirdparty.xml | modpacks.xml |
| --- | --- | --- |
| 执行环境直连 | DNS 阶段失败 | DNS 阶段失败 |
| 执行环境经可用上游代理 | 200，有效 `modpacks` XML，149197 字节 | 200，有效 `modpacks` XML，56155 字节 |
| 经本工具 CONNECT，再经同一可用上游代理 | 200，SHA256 与上一行完全一致 | 200，SHA256 与上一行完全一致 |

本环境直连的 DNS 限制不代表用户机器的 DNS 情况。经可达路径取得有效列表，说明端点在记录时仍可用；这不能保证所有网络都能访问，也不能证明每个历史整合包文件仍可下载。TLS 校验始终开启；测试环境的上游代理会提供其信任链，本工具没有为 CreeperHost 换发证书。

用户机器同时在直连和透传时失败，更指向其访问路径不可达、源站/CDN 对该路径的限制，或尚未给工具配置能访问该域名的上游代理。单凭这些日志不能在上述原因之间作最终归因。

### 改动与用户配置

**不修改 LegacyFTB 路由。** 未找到需要且可靠的合法替代端点，不加入解密名单，不关闭 TLS 校验，不造 XML，也不将网络错误包装为成功。新增回归检查锁定两个原始 URL 和签发名单行为。

若需要额外代理，应设置本工具的 `upstreamProxy`，而不是让它指向自身。示例 `http://127.0.0.1:7890` 仅表示另一个实际可用的 HTTP 代理；SOCKS5 地址不能直接填入。Windows 系统代理开关不等于 Node 的代理环境变量。配置后仍需在用户网络上确认该上游确实能取得这两份 XML。

原始记录：`test-results/legacy-ftb-origin-report.json`、`test-results/legacy-ftb-bridge-report.json`。

## CurseForge 大型整合包

### 证据与瓶颈

从 MCIM 所列 ATM10 8.5 归档中用 HTTP Range 读取并校验 `manifest.json` 的 ZIP CRC，得到真实 498 个项目 ID 和 498 个文件 ID。没有完整下载或验证整个约 206 MB 归档的 SHA1；不把清单读取当作整合包安装。

| `/v1/mods` 测量 | 结果 |
| --- | --- |
| 498 ID，identity | HTTP 200，Content-Length 8205577；25 秒仅收到 622332 字节，按观察预算中止 |
| 498 ID，gzip 单请求 | 25 秒收到 647161 压缩字节，仍未完整；此观察不等同于证明它必然超过 60 秒 |
| 50 ID，gzip | 785393 字节解压数据缩至 150846 字节，8215 ms 完成 |
| 10 ID，gzip | 178952 字节解压数据缩至 33352 字节，1580 ms 完成 |

响应体传输和等待明显大于 JSON 解析开销。原实现要求 identity，且把全部项目放进一次长响应；Prism 在完整 JSON 到达前一直没有收到回复。

最终 **1.0.1** 在 Linux 以 Prism 同样的字符串 ID、HTTPS CONNECT 和 POST 结构复测：

| 阶段 | 输入/返回 | 完整响应耗时 |
| --- | --- | ---: |
| `POST /v1/mods/files` | 498 文件 ID / 498 文件记录；只发一次请求 | 10743 ms |
| `POST /v1/mods` | 498 项目 ID / 498 项目；无缺失，10 批 | 22321 ms |

项目查询上游压缩字节共 1548099，解压字节共 8205667；JSON UTF-8 转换/解析累计约 61.82 ms。随后以独立 10-ID 查询比对完整项目字段，匹配。分批响应多出的少量 envelope 字节与单请求不同；返回对象字段未按“轻量列表”裁剪，只继续移除既有的 MCIM `sync_at` 扩展。

### 实现与错误语义

- `POST /v1/mods`：保留整数 ID 转换、可选请求字段和凭据隔离；每批默认 50 个去重后的 ID，每次请求最多 3 批并发，仍受全局并发上限约束。文件 ID 接口不套用这个分批器。
- MCIM POST JSON 协商 gzip，流式解压并分别限制压缩/解压体积。文件/JAR/资源转发仍保持原字节、Range/HEAD 和原有校验行为。
- 所有必要批次完成后才组装 `{data: [...]}` 并发送客户端响应头。普通 4xx/5xx、无效 JSON、异常项目 ID、不同的 envelope 均使整次查询失败；取消排队项并中止同组在途请求。
- 整体默认预算 45000 ms，包含排队、网络与解析；超时返回 504。未完成的批次不会变成“成功但缺少一部分模组”。
- MCIM 正常批量语义是只返回找到的 ID；某一整批全不存在时，它用特定的结构化 404 表达。仅当 `code/error/detail` 和请求 ID 全部精确匹配这一语义时才视作缺失；普通 404 仍失败。若所有 ID 都不存在，整次仍为 404；空输入保持上游 400。

原始测量：`test-results/bulk-upstream-benchmark.json`、`test-results/bulk-live-report.json`、`test-results/atm-manifest-provenance.json`。这些是有限的单轮功能检查，不是压力测试或持续性能保证。
